Deploying 50+ times a day without fear

How Etsy made releasing code so routine that any engineer could ship to production in minutes, and how a mid-size team can build the same habit without Etsy's in-house tooling.

01The challenge

When every release bundles weeks of changes, each deploy carries weeks of risk. Failures are hard to trace to a single change, rollbacks are painful, and teams respond by releasing even less often, which makes the next release bigger and riskier still.

02What Etsy did

  • Small changes, shipped continuously. Engineers pushed small diffs many times a day instead of batching them into large releases.
  • A one-click deploy tool. Deployinator, Etsy's in-house tool, turned a deploy into a button: build, run the automated tests, update staging, then push live.
  • Feature flags. New code went to production switched off ("dark"), then was turned on gradually, so deploying and releasing became separate decisions.
  • Pre-commit testing and a staging mirror. Changes could be tested against the full suite before commit, then checked on a staging environment that mirrored production.
  • Graph everything. The rule was that anything that can be graphed is graphed, so the effect of every deploy showed up on a dashboard within minutes.

03The results

By 2014 Etsy was deploying to production more than 50 times a day, with a CI setup serving around 150 engineers and running more than 14,000 test-suite runs daily [1].

The lesson: deploy frequency is a result, not a goal. It follows from making each change small, each deploy boring, and each failure visible and reversible.

04At your scale: a 90-day plan

You don't need a custom deploy tool. Managed CI and an off-the-shelf flag service give a 5–50 person team the same habit.

Days 1–30 · BaselineDays 31–60 · AutomateDays 61–90 · Make it routine
  • Measure the four DORA metrics as they stand today
  • Map every manual step between merge and production
  • Put infrastructure under version control, starting with one environment
  • One pipeline in GitHub Actions or GitLab CI: build, test, scan, deploy
  • One-click (or on-merge) deploys to staging and production
  • Automated rollback to the previous version
  • Feature flags for anything user-facing
  • A single dashboard showing errors and latency per deploy
  • Aim to deploy daily; review DORA metrics monthly

05Readiness checklist

  • Every change goes through a pull request and review
  • Tests run automatically on every push
  • A deploy takes one action, not a runbook
  • Any engineer can deploy, not one gatekeeper
  • Rolling back takes minutes
  • New features can ship switched off
  • You can see errors per deploy within minutes
  • You know your current lead time for changes
